| 验证标准 | 结果 |

## 2. 测试对象与方法

1. **建库**：`init_database(db, reset=True, validate=True)` 从零建库 —— 自动发现项目根
   `schema_v3.sql` + `seed_general_v3.sql`，产出 62 张表，`integrity_check` + `foreign_key_check` 通过。
2. **测试夹具**：种子没有「老鼠 / 石头」。为触发任务要求的 `猫抓老鼠`（can_do + 闭包）与
   `猫吃石头`（受事约束冲突）路径，补插 2 词 2 义项 + 类别 + 一条 is_a 边
   （`老鼠 is_a 动物`，source_id=5 与种子同源）。夹具 SQL 在脚本 `FIXTURE_SQL` 中逐行注释。
   夹具本身顺带验证了 **L4 触发器增量闭包**：插入 is_a 边后 `closure` 自动派生
   `老鼠→动物(1跳)、老鼠→生物(2跳)` ✅。
3. **双通道执行**：每句先手动串联五层方法做**逐阶段计时**（Phase 1–5），
   再调用官方 `parser.parse()` 取正式结果与耗时（Phase 6），两者互为交叉验证。
4. **断言台**：与 `validate_*.py` 同风格的 PASS/FAIL 计数；另设 **XFAIL** 档
   （「已知偏差」——观察到的真实缺陷，修复后应升级为常规 check）。

## 6. 发现的问题（端到端首次暴露，均未修复）

### K1 🔴 缺主语句被「倒装句」竞争压制，省略读法无法胜出
`吃鱼` → 倒装句(P=吃, S=鱼)，输出 **施事=鱼**（语义反转：变成「鱼吃」）。
主谓宾的省略读法（S 槽留空，8.50 分）输给倒装句（9.20）。
**建议**：① 倒装句模板要求 P 为不及物动词或带 `subcategory` 约束；② 或给「省略授权读法」
加篇章一致性加分（有上下文时主语可由前句补足应加分）。阳性对照 `把鱼吃了` 证明省略
机制本身（previous_subject 回填）工作正常——问题只出在**评分竞争**。

### K2 🔴 缺宾语句被「连动句」吸收，且同一实体被回填进两个宾语槽
`猫吃` → 连动句(S=猫, V1=吃, **O1=鱼, O2=鱼**)，conf 0.61。复合缺陷：
- a) 连动句的 V2/O1/O2 在 `pattern_slots` 里全是 `is_required=0` → 只有一个动词的句子也能匹配
  「连动」句式（连动句的定义就要求 ≥2 个动词，V2 应为必填）；
- b) 省略规则 rule=10（previous_mentioned）把上一句的「鱼」**同时**回填 O1 和 O2 ——
  同一先行语注入多个同角色槽位没有去重/次数限制。
**建议**：seed 层把连动句 V2 改必填；parser 层给「同一实体 → 多个同角色槽」的回填加上限（≤1）。

### K3 🟡 约束冲突不回传整体置信度
`猫吃石头` 的受事合法性 = 未通过(0.30)，但总分 0.854 与完全合法的 `猫吃鱼` **完全相同**。
下游无法凭 confidence 感知这句话有问题，必须读推理链。
**建议**：把 `constraint` 类推理的最低置信度纳入 `parse()` 总分加权（例如乘 0.6 或扣固定分）。

### K4 🟡 自相矛盾的推理输出
同一句 `猫吃石头` 同时给出：
`吃 --patient--> 石头 (典型论元, 0.90)` 与 `吃 --选择限制--> 未通过 (受事合法性, 0.30)`。
典型论元规则在类别不匹配时仍实例化了论元边。
**建议**：典型论元实例化前先过受事合法性检查；或冲突时降为 `吃 -X-> 石头`（否定边）。

### K5 🟡 受事合法性规则 SQL 只认 category 约束，feature 约束误判
`猫抓老鼠`：`抓` 的受事约束是 `kind='feature', value='+concrete'`，而推理规则
R4（受事合法性）的 `condition_sql` 把 `rc.value` 直接与 `sense_categories.cat` 比对 ——
`'+concrete'` 永远不在类别表里 → 具体名词「老鼠」被误判 **未通过(0.30)**。
**建议**：R4 拆成两条（category 走类别表、feature 走 `sense_features`），或 condition_sql 按
`rc.kind` 分支。

### 数据注记（低优先级，建议顺手核一遍种子）
- `schema_v3.sql` §14 给 **猫**（sense 2）挂了 `人工物` 类别（is_primary=0）——疑似残留；
- `relation_constraints` 有 `(1005 喝, patient, category, 无机物)` —— 「喝」的受事应为
  液体类，取值可疑。

## 7. 与单元测试覆盖率的对比分析

| 维度 | 单元测试（627 项） | 端到端（本脚本 68 项） |
|---|---|---|
| 对象 | 各层**组件契约**（connection/closure/parser 各自独立测） | 跨层**组装行为**（触发器闭包 → 解析器实时读取） |
| 数据 | 多数跑在既有库 / 程序化构造的库上 | `init_database` 从零建库（schema+seed 真实产物） |
| 断言口径 | 「组件做什么」（输入→输出契约） | 「系统该做什么」（语法/语义正确性） |
| 覆盖盲区 | **评分竞争**（多句式抢同一句）无人问津；省略回填只在受控单测里验证；置信度只测了公式没测语义 | 全部命中 |

单元 627 项全绿、e2e 仍揪出 4+2 个问题的原因很典型：**每个组件都符合自己的契约，但契约之间
的缝隙（评分竞争、双槽回填、冲突不回传、规则 SQL 与约束类型错配）没有任何一层的单测负责**。
这 4 个 XFAIL 对应的缺陷全部属于「缝隙类」，建议：
1. K2-a、K5 修在数据/SQL 层（seed + inference_rules.condition_sql）；
2. K1、K2-b、K3、K4 修在 parser 评分与回填策略层；
3. 每修一个，把对应 XFAIL 升级为常规 check（脚本已预留 `xmiss` 提示）。
