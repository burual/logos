### 关键技术结论（可复用）

1. **`PRAGMA foreign_keys` 默认 OFF** —— 不显式开启，所有 FK 声明形同虚设。必须在每个连接设置。
2. **`PRAGMA recursive_triggers` 默认 OFF** —— 触发器级联（删边→排队重建）不会触发，必须显式开。
3. **触发器体内不允许 `WITH ... INSERT`**（实测 `near "INSERT": syntax error`）。必须写成
   `INSERT INTO t(...) SELECT ... FROM (WITH RECURSIVE ...) AS X`。
4. **UPSERT 的 `DO UPDATE SET` 从左到右求值，后者可见前者结果**。所以
   `first_edge = CASE WHEN excluded.depth < depth ...` 必须写在 `depth = MIN(...)` **之前**，否则条件恒假。
5. **FTS5 中文必须双通道**：`trigram` 对 <3 字符查询命中 0 行（实测"动物"→0 行）；
   1–2 字高频词必须靠 jieba 预分词列 + `unicode61`。
6. **闭包表方向必须写进注释**：约定 `ancestor`=上位(更一般)、`descendant`=下位(更具体)。
   v2.0 只有列名没方向约定，极易写反（属性继承规则会取反）。
7. **闭包插入代价 ≈ (1+|src 下位子树|) × (1+|dst 上位链|)**。实测 6×3 树：叶子 1.15ms → 根 561ms。
   批量导入必须 `mode='off'` → 导入 → 队列统一重建。
8. **见证边 `first_edge` 不能加外键**：`ON DELETE SET NULL` 会在 AFTER DELETE 触发器**之前**清空值，
   导致失效逻辑静默失灵。用弱引用 + 触发器失效 + 队列重建。
9. **STRICT 表 + 生成列**可消灭 `char_count`/`is_separable` 这类派生字段的脏数据。

### 汉语言学发现（v2.0 结构性缺口）
- 只有语义角色、**没有句法成分层** —— 汉语是话题优先语言，主语≠施事是常态，两套必须并存。
- 缺：语素层（字≠语素）、音变规则（变调/轻声/儿化）、述补结构（动结/动趋/可能补语）、
  句类（陈述/疑问/祈使/感叹）、篇章层（话题链/零形回指）。
- 虚词应直接映射语义角色：`function_word_roles(把→受事/前置, 被→施事/前置, 从→起点/前置)`。
- 量词要走两级：个体显式搭配 + 类别默认（动物类→只），否则十万名词要建十万行。
- `ellipsis_rules` 的 PK `(context_type, slot_name)` 只允许一条策略 → 省略回填机制形同虚设，
  必须改为允许多策略 + priority + max_distance。

### 本轮踩到的两个解析陷阱（写检查器时容易误报）
1. `AFTER UPDATE ON senses` 中的 `UPDATE ON` 会被当成表引用 —— 必须**只扫 `BEGIN...END` 之间**的触发器体。
2. `BEFORE UPDATE OF c1,c2 ON tbl` 这种事件形式会让 `BEFORE|AFTER + \w+ + ON` 的正则**匹配不到**，
   导致触发器被漏统计（10 个只数出 9 个）。正确做法：先取触发器头（`BEGIN` 之前），
   再在其中找**第一个** `\sON\s+(\w+)`。

### 两条 WARNING（真实隐患，非形式主义）
- **T4（实测发现）**：SQLite **不在 CREATE TRIGGER 阶段**校验触发器体内的表名/列名 ——
  `CREATE TRIGGER ... BEGIN INSERT INTO 不存在的表 ... END` 能创建成功，错误延迟到 DML 期才暴露。
  所以触发器体拼写错误**无法在建库期拦截**，只能靠功能回归覆盖。
- **P1**：闭包重建触发器按 `r.src_id = w.cur` 关联 `relations`，而没有以 `src_id` 打头的索引；
  关系量过万时可补 `CREATE INDEX idx_relations_src_id ON relations(src_id) WHERE src_kind='sense';`。

### 其他实测结论（可复用）
- `WITH ... INSERT` 在触发器体内：`OperationalError: near "INSERT": syntax error`（确认不支持）。
- 触发器体内 UPSERT + `excluded` 伪表：**支持**。
- `INSERT ... SELECT ... FROM (WITH RECURSIVE ...)`：**支持**（唯一合法写法）。
- STRICT 表类型强制：写 TEXT 到 INTEGER 列被 `IntegrityError` 拒绝。
- 全文**未使用 `jsonb()`**，JSON 函数只有 `json_valid` / `json_object`（JSONB 仅出现在版本注释里）。

### 靠"设计缺失用例"实测出的 5 个真实缺陷
1. 🔴 **7 个 `is_transitive=1` 的关系缺 `closure_policy` 行 → 静默无闭包**。触发器条件写的是
   `(SELECT mode ...) = 'incremental'`，缺行时子查询返回 NULL → 比较为假 → 不报错不插入。
   缺失：`can_do/caused_by/entails/has_property/precedes/presupposes/topic_of`。
   **已修**（补 7 行：属性类 incremental/12，事件类 batch/8）+ 回归锁 5.0a。
2. 🔴 **`max_depth` 在增量/重建两条路径语义不一致**：增量卡的是递归项 `d ≤ max_depth`，
   而最终深度是 `L.d+1+H.d` → 实际上限 `2*max_depth+1`；重建严格 `≤ max_depth`。
   实测 max_depth=2 时增量 6 行（最大 depth=3）、重建 5 行（最大 depth=2）。
   **已修**：最终 `WHERE` 统一卡 `L.d+1+H.d <= max_depth`，`lo/hi` 只剪枝到 `max_depth-1`。
3. 🟡 **`relation_types.max_depth` 是死列**（无任何读取点），与 `closure_policy.max_depth` 双写且取值冲突
   （has_part 12 vs 8）。暂以 5.0b 断言 `closure_policy.max_depth <= relation_types.max_depth` 固化契约，**待决策**。
4. 🟡 **`incremental` 切到 `off` 时既有闭包行不被清理** → 陈旧数据（实测残留 3 行、2 行 first_edge 已悬空）。
   建议加 `tr_closure_policy_au`（AFTER UPDATE OF mode）清空 + 入队重建，**未擅自落地**。
5. 🟡 **`PRAGMA index_info` 不返回 DESC/collation** → 冗余索引探测器把 `(a DESC)` 误判为 `(a)` 会误删。
   **已修**：改用 `PRAGMA index_xinfo`，签名升级为 `(列名, desc, coll)`，只取 `key=1` 列，
   表达式索引（cid=-2）不作被删候选。加了阳性/阴性对照 5.13a-c。

### 踩坑：漏写 COMMIT，62 项行为测试全绿却掩盖了真实 bug
分块（Write + 多次 Edit 替换占位符）拼装大 SQL 文件时，最后一块把收尾的 `COMMIT;`
一起替换掉了，`BEGIN` 悬空。**62 项行为测试全部通过** —— 因为 SQLite 在连接关闭前
不回滚，同连接内读到的数据完全正常，隐式提交盖住了问题。只有当该脚本被当子步骤
嵌入更长流程、或进程在后续步骤才退出时，未闭合事务才会回滚、数据全丢。

补了三条断言（现 65 项）：
1. 静态：`BEGIN;` 与 `COMMIT;` 计数配对
2. `conn.in_transaction is False`（加载后不在未闭合事务中）
3. **换一个连接重开文件库再读**，比对行数 —— 同连接内读得到 ≠ 已提交

> 教训：**分块拼装 SQL 文件后，必须重新通读文件头尾**，别只跑测试。
> 事务配对这类"静态完整性"问题，行为测试天然抓不到。
> 通用做法：任何自带 `BEGIN` 的脚本，都配一条"配对 + 落盘"断言。

### 可复用技巧：闭包验证要看"差分对拍"而非数行数
用**独立实现的在线递归 CTE** 当物化闭包的 oracle，比对集合是否完全相等
（本项目里 is_a 各 8 对）。这是唯一能发现触发器"漏算/多算"的方法；
`validate_schema.py` 的 5.5c 与本文件的 §4 都用了这个套路。
注意**元组方向**：在线 CTE 输出 `(ancestor, descendant)` 与闭包表同序，
但若从 `relations` 直接推会得到 `(下位, 上位)`，比对前必须翻转。

### 三个"反直觉"的 SQLite 事实（全部实测，非文档抄录）
1. **`sqlite3.Connection` 不支持属性赋值，也不支持 weakref**
   （`AttributeError: no __dict__` / `TypeError: cannot create weak reference`）。
   但**子类实例两者都支持** → 用 `LogosConnection(sqlite3.Connection)` 承载元数据，
   `isinstance(conn, sqlite3.Connection)` 仍为真，对调用方透明。
   这是本模块唯一优雅的方案；用 `id(conn)` 注册表会有 id 重用风险。
2. **`PRAGMA query_only` 在 `mode=ro` 连接上读回 0** —— 它不是可靠的只读探测器。
   同理 `BEGIN IMMEDIATE` 探针在只读库上也**成功**（SQLite 到真正写入才取锁），
   同样无效。可靠做法：自己记录 `read_only` 元数据（或 `PRAGMA user_version` 回写探针）。
3. **`PRAGMA journal_mode=WAL` 在只读库上的报错延迟到 `fetchone()`**，
   只 `execute()` 不取行会静默吞掉错误。→ 所有 PRAGMA 赋值必须强制取回结果。

### 一处必须纠正的认知（此前判断错了）
**`sqlite3.complete_statement()` 底部是 SQLite 的 `sqlite3_complete()`，它能够**
正确识别 `CREATE TRIGGER ... BEGIN ... END;`，本库 10 个触发器全部完整切出、逐句执行 0 失败。
之前"它会把触发器体切断"的结论是**错的**，成因是探针自身的两个 bug：
把输出截断到 70 字符（看不到完整的触发器）、以及过滤 `--` 注释行时**连换行符一起删掉**
造成相邻 token 粘连。

自研 `split_statements()` 的真正价值是三条能力差异（已写成断言）：
① 返回**行号**（官方只给文本）；② 能拆**同一行多条语句**（官方按行累积会合并，
本库 schema 第 1642/1648 行正是这种）；③ 跳过**纯注释块**（官方各多出 1 条）。
数量：schema 自研 150 条 / 官方 151 条，差值恰为 1 个尾部注释块。

### 实测性能
- schema 150 条语句在文件库上：逐句 autocommit **4302 ms** vs 整包一事务 **37.5 ms**（**114.8×**）。
  所以 `_load_script` 对无顶层 `BEGIN` 的脚本自动包事务；带 `BEGIN` 的（如 seed）原样执行。
- `init_database` 首次建库 **169 ms**、二次执行 **74.5 ms**，产出表 62/视图 5/触发器 10/索引 34。
- `executescript` 两个副作用已实测确认：出错**留下未闭合事务**；
  执行前**隐式提交**调用方事务（`ROLLBACK` 报 `no transaction is active`）。

### 设计约定（后续代码应遵守）
- `isolation_level=None`（显式事务模式）；原子性一律用 `with transaction(conn)`。
- `close_connection` 遇到未闭合事务**默认回滚 + WARNING**，不静默提交（漏 commit 是 bug）。
- `configure_connection` 在 `conn.in_transaction` 时**主动抛 TransactionError**，绝不静默跳过。
- `get_memory_cache()` 返回 `MemoryCache(dict)`；缓存键必须用 `hash_key()`
  （内置 `hash()` 被 PYTHONHASHSEED 随机化，不能当持久键）。
- 只读连接构造 URI 必须用 `Path.as_uri()`（本项目路径含中文，手拼 `file:` 会打不开）。


## Logos 闭包维护层（logos/db/closure.py）

**任务**：编写闭包维护核心模块（全量重建 / 增量更新 / 上位下位查询 / 属性继承 / 不变量校验 / 批量导入开关）。

**交付物**
- `logos/db/closure.py` —— 主模块（29 个公开符号，含 8 个必实现函数 + 生成器版 + 便利函数）
- `validate_closure.py` —— 回归校验 **87 项全绿**（S0–S10）
- `docs/CLOSURE_LAYER.md` —— 层文档
- `logos/db/__init__.py` —— 补齐闭包层导出

### 实测踩坑（可复用，已就地修正 CLOSURE_DIRECTION.md）
1. **`cursor.rowcount` 对前导式 `WITH ... INSERT` 恒为 -1** —— CPython 的 sqlite3 按**首个关键字**
   判语句类型，`WITH` 开头不被识别为 DML。重建报告"写入 0 行"即此症。→ 改用 `Connection.total_changes` 差值。
2. **触发器体内失败的是「前导式 `WITH ... INSERT`」**（`near "INSERT"`），而
   `INSERT ... WITH ... SELECT` 在触发器内**其实合法**，Python 层三种写法都合法。
   （此前日志/文档把失败示例写成了 `INSERT ... WITH`，已更正。）
3. **oracle 列名方向陷阱**：递归 CTE 里 `anc` 固定为边的 src 端（下位）、`cur` 沿 src 向上走（上位）。
   `SELECT cur, anc` 得 **(ancestor, descendant)**，与 closure 表列序**一致**，不需要对调；
   我在 `_differential_check` 里对调了比较列 → I6 报出"缺 N/多 N"对称假阳性。→ CTE 列改名 `desc_id/anc_id` 根治。
4. **UPSERT `SET` 从左到右求值** → `first_edge` 必须写在 `depth` 之前；`first_edge` 不加外键（弱引用）。

### 设计结论（后续代码应遵守）
- 方向口径：`closure(ancestor=上位/一般, descendant=下位/具体)`；问"谁的上位"约束 `descendant`。
- 属性继承：`JOIN relations r ON r.src_id = c.ancestor`（上位持有属性），方向写反会取到子类属性。
- 批量导入：`bulk_import` 上下文（异常安全，先恢复触发再重建）；`policy` 策略置 `mode='off'`
  （schema 原生、可逆），`drop` 策略真删触发器。SQLite 无 `SET TRIGGERS DISABLED`。
- 索引：上位走 `idx_closure_relation_desc`，下位走 PK；两者均无全表扫描（`EXPLAIN QUERY PLAN` 断言）。
- 实测：121 节点树批量导入+重建 **53 ms**（闭包 452 行）。

## 句法-语义解析层（`logos/parser/syntax_parser.py`）

### 交付物
- `logos/parser/syntax_parser.py` —— 基于数据库模板的解析器（约 3500 行）
- `logos/parser/__init__.py` —— 包导出（异常/数据类型/主类/便捷函数/常量）
- `validate_syntax_parser.py` —— 回归校验 **PASS 214 / FAIL 0**（S0–S12，退出码 0）
- `docs/SYNTAX_PARSER.md` —— 层文档（含 13 例矩阵实测表 + 9 条踩坑清单）

### 架构要点（后续改动须遵守）
- **五段流水线**：`tokenize → match_pattern → fill_slots → annotate_semantic_roles → query_relations`，
  `parse()` 串联；每段都能单独调用、单独测。本层是**只读消费层**（仅 `persist=True` 写 `utterances`/`anaphora`）。
- **7 道闸门**（顺序即语义）：必填槽位 → 同形 → 关键虚词标记 → 短语结构专闸 → **词汇证据** → 硬约束 → 覆盖率。
- **唯一硬约束**是 `slot_constraints.kind='marker'`；其余软约束只扣分 + 点名（`✗ [P] definiteness=… ……`）。
- **模板 `/` 两种语义**：独立 `/`（两侧有空格）= 变体分隔；紧贴 `请/别` = 字面量同义候选。
- **离合词两条路径都要做**：整体出现→切分（`words.separator_pos`）；拆开出现→重组（`bound_objects`，中间标 `infix`）。
- **虚词改写只认紧邻介词**（跳过可跳过成分后只看一个位置），不许回溯越界。
- **省略授权**：可选槽位可留空；必填槽位仅当角色 ∈ `ellipsis_rules.slot_role` 时可省略，且**一次至多 1 个**。
- **推理链主语用 `SemanticRole.entity`（中心语词形），不用 `text`（整段表层形式）**。
- **多父类渲染成并列 + 距离**：`鱼 的上位：动物(1跳)、食物(1跳)、生物(2跳)`，不得串成单链。

### 实测踩坑（可复用）
1. **闸门在计算之前读了统计量** —— 闸门 ⑤ 判 `parse.known == 0`，而 `known` 由后置的 `_score` 统计，
   于是读到 dataclass 默认值 `0`，**把所有正常句一票否决**（`pattern`/`mood` 全变 `None`）。
   → 抽 `_lexical_evidence()` 作唯一真源，在闸门处**现算**。**教训：跨方法共享的统计量，必须先算再判。**
2. **单字兜底让规则永不生效** —— `_oov_token()` 只拿到一个字符，`_guess_pos` 的"数词"分支
   对阿拉伯数字**永远不可达**（`2026` → 4 个 `?`）。→ 新增 `_oov_run()` 合并连续同类字符。
3. **`_persist` 先于 `_remember`** → 首次落盘写 `seq=0`，违 `CHECK (seq >= 1)`，
   被 `except sqlite3.Error` **静默降级**（`persist=True` 从未真正生效）。→ 调整顺序。
4. **落盘字段与事实不符** —— `anaphora` 一律写 `form='∅', form_type='zero', node=NULL`，
   哪怕回填的是 `猫`。→ 写入真实 `form`/`form_type`/`antecedent_node_id`，`use_db_context` 才能往返。
5. **写校验断言前先看 dataclass 字段** —— 我误把 `to_dict()` 的键写成 `slots`（实为 `filled_slots`）、
   误以为 `SlotFill.as_value()` 恒返回 list（实为单 token→`Token`）。**断言写错要改断言，不是改代码。**
6. **`shutil.copyfile` 在 Windows 上会因残留连接句柄失败**（Errno 22）——
   校验脚本里复制的库若连接未关，`unlink` 静默失败后复制即报错。→ 用完显式 `close()`。

### 设计结论
- **OOV 分级兜底**：封闭类词表 → 数词 → 指示代词 → 方位后缀 → `pos='?'`。
  `_CLOSED_CLASS_FALLBACK`（90 词）是**临时桥梁**，兜出来的词 `entry_id is None` 会计入 OOV 轻罚（1.2），
  以此持续暴露"词典缺项"；词典补齐后应逐项删除。
- **典型论元判据**：`吃 --agent--> 「动物」` + 句面 `猫` 与「动物」同属类别 → 匹配。
- **规则引擎**：链式前提必须**跨边合一**（`edge(A,rel,B) ∧ edge(B,rel,C)` 单边匹配做不到）；
  穷举边时上下位各扩 `max_hops=2`，再用 `focus`（结论主语 ∈ 本句概念）过滤扩张带来的无关推导。
- `SELECT 1` 类 `condition_sql` 的返回值是**占位**，不能当义项 id 渲染。
